# Historical airport identity (Keepraw Airport History)

Keepraw Fly identifies the **physical airport a code meant on the flight date**,
using the complete data of
[keepraw/airport-history](https://github.com/keepraw/airport-history) at one
pinned commit. A 1997 `HKG` flight is Kai Tak; a 1999 `HKG` flight is Chek Lap
Kok; a code that history does not settle is kept and shown as unresolved.

## Data package

`packages/core/data/airport-history/` is generated by
`scripts/update-airport-history.py` from upstream commit
`19b7b1decfe2b43916fd4607b049ebb79293ae77` (formal data `0.10.0`, schema
`3.0.0`) and is committed to this repository. The application never contacts
GitHub or an API at run time, and no GitHub Actions artifact is a data source.

| Path                                                               | Layer      | Content                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------ | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `formal/airports.json`                                             | formal     | Upstream `data/airports.json`, byte for byte: 37 physical airports, 52 IATA/ICAO assignments, 101 sources and 3 names, with `validFrom`/`validTo` `earliest`/`latest`/`precision` bounds                                                                 |
| `observations/iata.<h>.jsonl.gz`, `observations/icao.<h>.jsonl.gz` | candidates | Every IATA (9,599 codes) and ICAO (10,739 codes) reference-code observation (64,351 rows) with each physical-location hypothesis, source, kind, side, candidate, commit, blob and `revisionObservedAt`                                                   |
| `observations/records.<h>.jsonl.gz`                                | candidates | All 86,950 worldwide reference records (identifiers, location hypotheses, snapshot locator). GPS/LOCAL/IDENT observations are exactly identifiers × locations; the builder re-derives them and checks the upstream count (233,567 observations in total) |
| `observations/search-index.jsonl.gz`                               | candidates | IATA/ICAO code, site and name rows for historical-name search                                                                                                                                                                                            |
| `transitions/groups.<h>.jsonl.gz`                                  | candidates | All 88,330 event groups with their 117,356 selected candidates (classifications, status, physical match, before/after changes, possible sites, source entity, commits and blobs)                                                                         |
| `transitions/codes.<scheme>.<h>.jsonl.gz`                          | candidates | Self-contained per-code index of the 56,333 transition code observations (2,830 IATA and 18,484 ICAO codes)                                                                                                                                              |
| `transitions/code-reuse-leads.jsonl.gz`                            | candidates | The 493 geographically distinct code-reuse leads                                                                                                                                                                                                         |
| `licenses/`                                                        | licence    | Upstream CC0 data dedication, airportsdata MIT notice and upstream third-party notices                                                                                                                                                                   |
| `manifest.json`                                                    | —          | Upstream commit, counts, sharding rule and, per file, SHA-256 (bytes and content), size, record count, layer and schema version                                                                                                                          |
| `source-lock.json`                                                 | —          | Upstream commit and tree, builder hash, transient SQLite hash and metrics, and the SHA-256 of every raw upstream input                                                                                                                                   |

`<h>` is the first hex digit of `sha256("SCHEME:CODE")` (or of the group or
reference ID). Files are canonical JSON lines in stable order, gzip level 9
with an empty name and `mtime` 0, so two builds are byte-identical. The package
is 103 files and about 39 MB in Git. The web build ships only the code,
observation and search shards (about 10.7 MB) and fetches just the shards an
archive's codes need, each verified against its manifest SHA-256. The 156 MB
SQLite database the upstream builder produces is a transient build product and
is never committed or bundled.

### Updating

```sh
python3 scripts/update-airport-history.py --commit <new upstream commit>
pnpm test
```

The script fetches that upstream commit, runs the upstream full-corpus builder
`bulk/worldwide.py build` unchanged (it verifies every pinned input hash),
exports the package and fails if any count differs from upstream. Review the
diff and open a normal pull request. CI's `airport-history` job runs
`python3 scripts/update-airport-history.py --check`, which rebuilds the package
from the pinned commit and requires every file to match byte for byte.

## Resolution

`resolveAirportAtDate(code, date, scheme)` in
`packages/core/src/airport-history.ts` queries both layers in this order:

1. **Formal assignments.** With upstream's conservative half-open interval
   rule, a date inside one airport's _certain_ interval is `resolved` with its
   `airportId`. A date inside only the outer `earliest`/`latest` bounds is
   `uncertain`; several certain airports are `ambiguous`. An `unknown`
   precision is never turned into an exact date, and `verified` does not mean
   every day of the interval is known. The current directory never overrides a
   formal uncertain answer.
2. **Worldwide candidates.** Without a formal assignment for the date, every
   observation site and transition lead for the code is returned
   (`historical_candidate`), each possible site separately, with event group,
   candidate, reference and location IDs, coordinates, names, countries,
   sources, commits, blobs, classifications and original candidate status.
   Candidates never become an `airportId`.
3. **Current directory** (`current_directory_only`): no formal history, and
   every candidate site (if any) is the current directory's own site within
   10 km.
4. `unknown_code`. `candidate_index_unavailable` means the candidate shards for
   that code are not loaded yet; formal resolution still works.

`revisionObservedAt` is when an upstream directory revision was observed. It is
never a code effective date, a directory edit is never an allocation date, and a
current OurAirports row never proves a historical IATA/ICAO allocation.

## Use in the app

`packages/core/src/flight-airports.ts` resolves each flight endpoint:

- the origin at the departure airport's local `serviceDate`;
- the arrival from the real `actualArrival ?? scheduledArrival` instant in the
  historical arrival airport's IANA zone (the diversion airport when diverted);
- a stable statistic key: `airport:<apt_…>` for formal airports and
  `current:<IATA>` for current-directory-only airports. An `uncertain` date
  counts under the formal `airportId` only when exactly one formal airport is
  possible, the date is past that assignment's latest start (only the review
  horizon is open) and the current directory places the code at the same site.

Passport and yearly statistics count physical airports by these keys,
`currentDirectoryAirports` reports how many rest on the directory alone, and
`unresolvedAirports` counts endpoints that are not determined; those are never
merged into another airport. Routes and distances use only confirmed
coordinates; candidate sites appear on the Passport map as dashed "possible
location" marks and never as a route end or a distance input. Flight Detail,
search, the editor's airport field (historical names, codes and candidate
sites), Flighty, CSV and Umetrip imports use the same identities.

### Unknown airports never drop a flight

A well-formed three-letter code is kept even when no layer knows it
(metropolitan city codes such as `TYO` are still rejected). Times are never
assumed to be UTC:

- RFC 3339 times with an offset are kept as written;
- a determined airport uses its flight-date historical zone;
- several candidate zones are never auto-picked;
- a wall-clock time at an undetermined airport waits for the user's IANA zone
  or `±HH:MM` offset: the editor shows a time-zone field, and imports show an
  actionable pending list before anything is converted.

A user-confirmed zone is stored in the flight's `keepraw-fly.airport-timezones`
extension (`origin`, `destination`, `divertedTo`), so editing keeps it. The
Keepraw Fly JSON format is unchanged.
