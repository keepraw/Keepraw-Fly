# Multilingual regression and release quality audit

Audit date: 2026-10-13 (UTC). Baseline: `0c1b754f91ea2a232f7dff8cff660af70e786233`, the latest `main` when this audit started. Both merged PRs [#56](https://github.com/keepraw/Keepraw-Fly/pull/56) and [#57](https://github.com/keepraw/Keepraw-Fly/pull/57) are ancestors. ## Findings and changes

Two reproducible defects warranted changes:

1. **Malformed persistent locale cache prevented recovery.** A cached response containing `{broken` made every French language load reject before attempting the network. Clearing the in-memory rejected promise did not repair the persistent entry, so retry remained broken even online. The loader now removes only the unreadable locale response and fetches its current URL. Offline failure still retains the current UI; a later online retry repairs the cache. Archive and preference storage are separate and untouched.
2. **German aircraft registration label overflowed narrow editor fields.** In the expanded flight editor at 320px, `Luftfahrzeugkennzeichen` required about 155.4px in a 114px field. Its text extended beyond the modal's content edge. Editor label spans now allow wrapping within their fields. Input values, aviation codes and Detail gate labels retain their existing behavior.

No translations, archive schema, timestamp semantics, business calculations, storage adapter, import rules, dependencies, locale framework, remote services or CI configuration changed. The 15-second sequential warming policy remains unchanged.

The regression additions are bounded: one loader unit test, one German field-geometry browser test and one malformed-cache/offline-retry browser test. The existing preference regression now includes a canonical loyalty account and unknown archive extensions; Chromium switches and reloads all ten languages. Firefox/WebKit retain that test's original four-language native-storage smoke to avoid duplicating the business matrix. No existing assertion, browser tag, CI job or required gate was removed.

## Warming and performance

The timer starts after airport bootstrap and App archive/preferences loading finish. With the browser clock controlled, no locale fetch occurred through 14,999ms; at 15,000ms warming began. The loader fetches sequentially and stops when `navigator.onLine` is false. US English is bundled and does not require a fetch. A second warming pass made zero additional network requests.

The nine independent production resources total **312,108 bytes raw** and **88,585 bytes with local gzip compression**, excluding HTTP headers. Six newly added full resources are roughly 10.9–11.5KB gzip each; the UK override is 498 bytes gzip. Actual transfer depends on the host's compression and browser HTTP cache. The nested-path Python static server used uncompressed responses.

A cold Chromium development session, with garbage collection before and after warming, observed total JS heap usage rise from 17,934,204 to 18,565,040 bytes: about **0.63MB**. This includes other live page activity and is a single observation, not isolated locale allocation or a production memory benchmark. CacheStorage held nine response bodies; an inserted previous-release URL remained as a tenth entry and was ignored by the current loader.

At 64kbit/s, body transfer alone has a theoretical lower bound of approximately 39 seconds uncompressed or 11 seconds gzip, before latency. Warming does not inspect `saveData` or connection speed and may compete with later user activity. No measured user-visible performance regression justified changing the current policy in this audit.

Remaining cache risks:

- Successful loads remain in memory for the page lifetime. CacheStorage retains changed content hashes from previous releases; there is no pruning or retention limit. Unchanged hashes are reused. Nine completely changed resources would add approximately 312KB of response bodies per version, plus browser overhead.
- Cached locales can switch offline after an online page reload. This is **not** a guarantee that a fresh page navigation works offline: there is no service worker, and the HTML/JS/airport assets have separate browser-cache behavior.
- A newly deployed resource hash needs an online fetch before that version can switch offline. Browser clearing/eviction or denied cache access removes that guarantee. The current language and local flight archive remain available when a switch fails.
- Cleanup needs an explicit retention design that considers older open tabs; this audit does not delete valid old resources speculatively.

Normal loading makes the same requests and writes the same cache entries after the fix. A corrupt entry adds only its necessary replacement request. Same-tool local gzip measurements against the independently built baseline:

| Asset    | Baseline raw / gzip bytes | Final raw / gzip bytes | Gzip delta |
| -------- | ------------------------- | ---------------------- | ---------- |
| Entry JS | 556,797 / 163,459         | 556,846 / 163,475      | +16 bytes  |
| Main CSS | 138,773 / 22,584          | 138,878 / 22,595       | +11 bytes  |

These use Node's default gzip compression consistently; Vite's rounded size report uses its own compression settings. Locale resource bytes are unchanged.
